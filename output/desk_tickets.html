3 · Which part would have been simpler as a single agent with tools

Ticket 102, all of it. A single agent needs four calls: get_ticket, check_cash, request_payment_approval, update_ticket. The team made 11 tool calls and 3 delegations across 4 agent turns to reach the same answer. Nothing in a rent notice needs a second opinion.

Evidence: Ticket 102 tab → Expected → 3 · MCP tools: the plan itself needed only Boss, Facilities and Accounting and six tool names · Actual → Tools they called: four agent turns (Boss, Facilities, Accounting twice) for the same four calls

The fact-gathering in 101. Stock, vendor, invoice and cash are four reads that depend on each other. One agent holding all four results in one place can see that 501 is the blocker. In the team, each agent re-read the ticket, and the facts travelled between agents as English sentences, which costs tokens and loses detail. Accounting’s first turn even said the invoice could be prepared and stopped, and the request only happened when Inventory asked.

Evidence: Ticket 101 tab → Actual → What the agents actually did: steps 2 and 3 are Accounting being asked about invoice 501 twice, once by Boss and once by Inventory

The cash arithmetic in 103. In the first full run this is where splitting hurt most: the Boss reasoned over Accounting’s summary rather than the check_cash data and double-counted invoice 501, claiming a $680 shortfall. I fixed it in the tool, not in the team: check_cash now lists what is already committed, and in this run the Boss and Accounting got it right ($264.00 needed, $152.00 free) and the tool refused the order anyway. So the real protection was the tool and its numbers, and a single agent with the same tool would have had the same result.

Evidence: Cash tab → Item by item: one subtraction, $3,400.00 − $840.00 − $8.00 − $2,400.00 = $152.00 · ticket 103 Actual: the refusal at $264.00 against $152.00

The later passes made this argument stronger. Resolving the three tickets took 9 runs and 349,012 tokens, against 177,143 for the three first passes, and 13 runs and 491,131 tokens in the first full run. Every one of the fixes that mattered was in a tool or in a person, not in the number of agents: a payment history in get_ticket (102), a guard against ordering the same thing twice (101), a way to record that stock arrived (101), a way for a person to say how a ticket ends (103). None of those needed a sixth agent.

Why splitting did not buy me much here. All five agents had the same 16 tools, so the “specialists” differ only by prompt. The real protections are not agent boundaries at all: the pay tool is hidden from every agent, amounts come from the database, and the duplicate was refused by the tool. A single agent with the same tools and the same hidden tools would be exactly as safe.

What I would keep from the team. Writing a customer message under its own rules (no dates, no internal details, and no price the Boss has not confirmed) and a final decision-maker who reviews before a status or a discount is set. I would keep those as two light steps around one operator agent, not five agents talking to each other. The audit trail by role is also nicer to read with several agents. A team starts to earn its cost only when the specialists have different tools or data, for example a real accounting system, an email system and a warehouse system.

5 · Three new problems it cannot solve, and what I would build

A. A customer returns a hoodie and wants a refund

Why it cannot. The shop has no sales at all: no orders, no revenue, and cash only goes out. Nothing can say what the customer paid or whether the return window is open, and no tool can put money back.

Tools needed: new tables orders, order_lines and refunds; get_order(order_id), record_sale, request_refund_approval(order_id, amount, reason) that prepares the refund for a human exactly like a payment, execute_approved_refund (human only, hidden from agents), and restock_returned_item. A read-only link to the payment processor to confirm the original charge.

Agents needed: a Returns agent that applies the policy (window, condition, who pays shipping), Accounting extended to handle money coming in as well as out, and Customer Service to write the reply. Identity checks would matter here: I would not let an agent refund anyone it cannot match to an order.

Evidence: Cash tab: its header says “cash only goes out, no revenue is modeled”, and every row in Item by item can only be an outflow · ticket 101 tab: Facts the team should find lists only the ticket and vendor invoice 501; nothing the customer paid is recorded anywhere

B. Chasing a vendor or updating a customer for real

Why it cannot. I deliberately built no way to contact anyone: drafts stay on the board. So the team cannot actually email Bulldog Print Co to rush a reprint, text Tauhid that his tee is delayed, or read a reply that arrives. By the end of this run four drafts for Tauhid and five for Yale AI Club sit on the board, and none has been sent.

Tools needed: an outbox. queue_message(to, subject, body) puts a message in a table outbox; a human approves it; send_approved_message (human only) sends it through an email or SMS service. Also a contacts table with an allow-list of recipients, templates, rate limits, delivery and bounce status, and an unsubscribe rule. For incoming mail, read_inbox that turns a reply into a new ticket.

Agents needed: a Communications agent that owns the outbox and tone, handing drafts from Customer Service and Inventory to it; and an Intake agent that reads replies and opens tickets. The key rule would stay the same as for payments: the agent prepares, a human sends.

Evidence: Ticket 101 tab → Actual → How it ended: draft 4 says the tee is ready, but nothing tells Tauhid · ticket 103 Actual: drafts 5 to 9 are all unsent, and the 5-day vendor lead time was never chased

C. Tracking orders and planning ahead (I built only the smallest piece)

Why it cannot, fully. I added one piece after the first full run: a human confirms that a paid purchase order arrived (receive_shipment), and only then does the stock go up. I also added a guard that refuses a second request for something already approved and paid on the same ticket. That fixed the duplicate: in the first full run the team ordered the same tee twice (payments 3 and 4, an unintended extra $8.00), and in this run it ordered once. But it is a patch, not tracking. Nothing records an order between “paid” and “received”: no status, no expected date, no way to notice a late delivery, and a second ticket for the same tee would not know one is already on its way. There is also still no sales history, so nobody can say what to reorder or when the money will run out.

Tools needed: a purchase_orders table with a status (ordered, shipped, received) and an expected date, so a second order for the same thing shows up as already on its way; track_order(po_id); a sales_history table; forecast_demand(sku, days) and forecast_cash(days) that project spending against rent and invoices still to come.

Agents needed: a Receiving agent that matches deliveries to orders and flags short or late ones, and a Planner agent that proposes reorder points and warns the Boss before cash gets tight, so a gap like the one in ticket 103 is caught in advance.

What I would change next

  • Make delegation sequential by default. Have the Boss ask one specialist at a time unless the questions are truly independent, and tell it which agents already hold the answer, so Accounting is not asked twice. (#101, #102, #103 Actual, Differed)
  • Define “resolved” for each kind of ticket before the run. In the first full run the Boss would not close 101 until a person said a saved draft was enough. In the rerun it closed 101 by itself, but 103 still needed a person because the ticket names no price. A short rule per ticket type (customer order, rent, price override) would settle both. (#101, #103 Actual, How it ended)
  • Show the money history from the start. I only added payment history, the rent-paid explanation and the no-reorder guard after the agents got it wrong in the first full run. They should have been there on day one. (#102 and #101 passes)
  • Stop duplicate reads. Pass the ticket facts along in each request so the specialists do not each re-read the same ticket. (#101 Actual → Tools they called: four get_ticket calls)
  • Put the cash rule where it cannot be missed. A line in the Accounting prompt: free cash is the balance minus the pending approvals, and show the arithmetic. I already made check_cash list the pending approvals so nothing is counted twice.
  • Keep the Boss from offering what we cannot fill. Require at least three tested prices before any discount decision, and require the Boss to state how many units the offer covers: in this run it authorized $46.40 for all 20 hoodies when only 8 exist. (#103 Actual: two prices tested, offer for 20)
  • Let a failed run say so, and offer a retry. A run that fails sets no status and does not start itself. Ticket 103’s second run failed after five timeouts in a row, and the ticket sat there until a new run was started by hand. The dashboard shows the failure, but it should offer “try again” and the Boss should be told a run was lost. (#103 Actual → How it ended, pass 2)
  • Fix the stalls. Model requests stall now and then, always inside a Customer Service turn after a draft was saved or listed. In the first full run three requests stalled (ticket 101’s first run twice, ticket 103’s second run once) and the retries recovered all three. In this run seven timed out: two on ticket 103’s first pass (recovered) and five in a row on its second pass, which is the first time the retries did not recover and a run failed. I tested earlier that the same request sent on its own, with no agents involved, also stalls (2 of 12, and 2 of 24 on a fresh connection each time), while a tiny request never did (0 of 24), so the cause is in the gateway or provider, not in my agents, and I cannot fix it from here. The timeout is 30 seconds and every stalled attempt is recorded in the audit trail. The token totals count only requests that came back, and a failed run records none. (#103 Actual: 146 seconds on pass 1, a failed pass 2)
